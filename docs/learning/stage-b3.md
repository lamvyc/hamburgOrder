## 2. 一句话本质

B3 的本质不是“把 OFFSET 换成 id > ?”，而是：**游标必须对应唯一稳定排序，查询必须真正利用索引，并且要承认优化器、数据分布和维护成本。**

## 3. 阅读问题

1. `LIMIT 5 OFFSET 1000` 为什么越翻越慢？新增/删除行时还会出现哪些重复或漏项？
2. 为什么 keyset 排序键必须有唯一兜底？如果只按 `created_at` 排序，同一毫秒的多行会怎样？
3. 为什么查询取 `limit+1` 条就能判断 `hasMore`？相比单独 `COUNT(*)` 有什么优势与限制？
4. 加了 `(store_id, id)` 索引，为什么 EXPLAIN 仍可能选择唯一键 + filesort？此时 FORCE INDEX 的收益与风险是什么？
5. 翻页期间新增/删除游标前后的商品，下一页可能出现什么？哪些是可接受语义，哪些是 bug？

## 4. 独立开发任务

**任务：管理员审计日志游标分页。**

```text
GET /api/admin/audit-logs/page?limit=20&beforeId=
```

要求：

- 按 `id DESC` 稳定排序；
- `beforeId` 取更旧记录；
- limit 1–100；
- 不返回总数；
- 增加 `(action,id)` 或评估现有索引；
- 受控数据 EXPLAIN；
- 补不重不漏、权限、空页测试；
- 不修改现有审计写入。
