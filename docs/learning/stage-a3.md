## 1. 知识定位

层级：**L2 — 数据库事务、条件更新、唯一约束、并发、幂等、订单快照**。

本轮真实用到了：

- Spring `@Transactional` 与 `Propagation.MANDATORY`
- 数据库唯一约束作为幂等并发门闩
- `SELECT ... FOR UPDATE`
- 条件 UPDATE 与影响行数
- 固定锁顺序
- 订单/明细/库存/流水/事件同事务
- BigDecimal 与成交快照
- 前端幂等键持久化与购物车指纹
- 真实并发测试与最终状态断言

## 2. 一句话本质

A3 的本质不是“插入一张订单表”，而是：**服务端在同一个事务里，用数据库条件和唯一约束决定“这笔订单能不能成立、库存是否只扣一次、同一个请求是否只执行一次”。**

## 3. 阅读问题

1. 为什么下单请求不传价格？服务端如何防止客户端改价？订单明细中的名称和单价为什么需要快照？
2. 库存 SQL 为什么必须把 `available >= ?` 放在 UPDATE 的 WHERE 里，而不是先 SELECT 再判断？影响行数为 0 时应该怎样处理？
3. 同一 Idempotency-Key 的两个并发请求，数据库唯一约束、事务、`SELECT ... FOR UPDATE` 各起什么作用？为什么不能只用前端按钮禁用？
4. `InventoryService.reserve()` 为什么使用 `Propagation.MANDATORY`？如果改成 `REQUIRES_NEW`，多商品第二项失败时会发生什么？
5. 订单详情为什么对其他顾客返回 404 而不是 403？如果员工需要看门店订单，A4 应如何设计权限与查询？

## 4. 独立开发任务

**任务：新增 `GET /api/orders` 个人订单列表，使用游标分页。**

约束：

- 只返回当前 CUSTOMER 的订单；
- 稳定排序：`created_at DESC, id DESC`；
- 参数 `limit`（1–50）与 `beforeId`；
- 游标不能使用 OFFSET；说明为什么相同 `created_at` 也必须用 id 兜底；
- 返回必要的订单摘要（id、orderNo、storeName、status、totalAmount、createdAt），不返回全部明细；
- 补真实 MySQL 集成测试：两个顾客隔离、分页不重不漏、响应顺序稳定；
- 不修改 POST /api/orders 的幂等语义。

建议先写 SQL 与索引，再写接口；用 `EXPLAIN` 记录执行计划。

2. 如何区分“前端每次点击都换 key”“页面刷新丢失 key”“key 相同但请求 hash 不同”“后端唯一约束没有生效”？
3. 给出至少两条 SQL 或浏览器 DevTools 证据。
4. 为什么“按钮 disabled”无法解决这个问题？
