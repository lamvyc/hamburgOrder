## 1. 知识定位

## 2. 一句话本质

C1 的本质不是“加个 Redis”，而是：**缓存必须有明确的事实来源、TTL、写后失效和故障降级；缓存命中的前提是数据仍然正确。**

## 3. 阅读问题

1. 为什么 cache-aside 读失败要回源，而不是让菜单直接 503？BYPASS 与 503 的语义差别是什么？
2. 为什么管理员改价后要在事务提交后删缓存，而不是事务中途删？中途删除可能被哪个并发读写回旧值？
3. TTL 60 秒意味着管理员改价后最坏多久可见？如果要求秒级一致，需要什么机制？
4. 缓存穿透、击穿、雪崩分别是什么？C1 当前实现了哪些、没实现哪些？
5. 为什么非缓存集成测试要 `app.cache.menu.enabled=false`？如果它们连开发 Redis，会发生什么？

## 4. 独立开发任务

**任务：菜单缓存命中率与 single-flight 防击穿。**

要求：

- 暴露 HIT/MISS/BYPASS 计数（Actuator/Micrometer 或只读端点）；
- 同一门店并发 MISS 时只允许一个回源，其余等待/复用；
- Redis 故障时仍可回源；
- 不改变菜单响应体/X-Cache 语义；
- 补并发测试与 Redis 故障测试；
- 不做多实例广播。

## 5. 故障定位练习

**场景**

管理员把价格从 32 改成 33，管理台显示成功；公开菜单仍显示 32，持续 40 秒后恢复。

请排查：

1. 先查哪三个证据？
2. 如何区分“未删缓存”“事务回滚但仍删缓存”“删除后又被旧值写回”“Redis 有多个 key/实例”“前端/网关缓存”？
3. 给出两条 Redis/HTTP 证据。
4. 修复应放在事务边界、删除顺序、TTL 还是多实例失效？

## 6. 脱稿口述题

> “菜单缓存如何命中/回源？管理员改价后如何失效？Redis 挂了菜单为什么还能打开？TTL 与一致性如何取舍？”

要求：

- 提到 cache-aside、afterCommit、TTL、BYPASS；
- 说明一个并发写回场景；
- 不照读代码。
