# 阶段 A4 学习材料

> 先提交分析或代码，再给答案。提示顺序：排查入口 → 局部线索 → 原因分析 → 完整解法。

## 1. 知识定位

层级：**L2 — 状态机、条件更新、权限数据范围、事务事件、过期校验、并发确认**。

本轮真实用到了：

- 订单状态机
- `UPDATE ... WHERE status=?` 条件转换
- affected rows 与 409 冲突
- 支付只提交 reserved，不重复扣 available
- 员工 membership 数据范围
- 事件与状态转换同事务
- 过期支付拦截
- 支付并发只成功一次
- Playwright 顾客/员工跨角色流程

## 2. 一句话本质

A4 的本质不是“加几个按钮”，而是：**订单状态只能由合法的前置状态、正确的权限和实际影响行数共同推进，并且状态与事件必须在同一事务里。**

## 3. 阅读问题

1. 支付时为什么只减少 `reserved`，不再次减少 `available`？如果支付 SQL 再扣一次 available，会出现什么库存错误？
2. 支付的条件 UPDATE 为什么同时包含 `user_id`、`status='WAIT_PAY'` 与 `expires_at > now`？被影响行数为 0 时如何区分过期、状态已变和越权？
3. 员工开始制作时，为什么不能相信前端传来的 storeId？`StaffOrderService` 如何同时校验 membership 与前置状态？
4. 状态更新和 `order_events` 为什么必须在同一事务？如果事件写入失败但状态提交，会怎样？
5. 两个员工同时点“开始制作”，条件更新和事件写入如何保证只产生一次有效转换？重复操作的响应应该是什么？

## 4. 独立开发任务

**任务：新增员工订单历史列表 `GET /api/staff/orders/history?storeId=&status=&limit=&beforeId=`。**

约束：

- 仅 STAFF，且 membership 校验；
- 只返回 COMPLETED/CANCELLED；
- 游标 `created_at DESC, id DESC`，不能用 OFFSET；
- `status` 可选，校验只允许 COMPLETED/CANCELLED；
- 返回摘要，不返回明细；
- 补两个员工门店隔离、分页不重不漏的测试；
- 结合 EXPLAIN 说明索引是否满足过滤与排序。

不要提前实现 A5 的取消接口。

## 5. 故障定位练习

**场景**

员工看到订单处于 WAIT_MAKE，快速双击“开始制作”。数据库最终出现两条 `MAKING_STARTED` 事件，但订单只从 WAIT_MAKE 变成 MAKING 一次。

请在不修改代码的前提下排查：

1. 先查哪三个证据？
2. 如何区分“状态更新没有条件”“事件在另一个事务”“前端重复请求”“事件插入缺少唯一/幂等约束”？
3. 为什么订单状态只变一次，事件却可以重复？
4. 给出至少两条 SQL/HTTP 证据；说明修复应放在哪一层。
