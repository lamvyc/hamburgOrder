# 阶段 B5 学习材料

> 先提交代码/分析，再给答案。

## 1. 知识定位

层级：**L2 — dry-run、逐行校验、只读预览、TOCTOU、错误码设计**。

本轮用到了：

- 预览与执行分离
- 逐行结果结构
- 不写库存/批次/流水/审计
- 预计前后值
- 预览后库存可能变化（TOCTOU）
- 前端预览 UI
- 错误码与行号

## 2. 一句话本质

B5 的本质不是“再跑一遍校验”，而是：**预览必须是纯读、逐行可解释，并且明确它不承诺执行成功；正式写入仍由幂等事务重新决定。**

## 3. 阅读问题

1. 为什么预览不应该写 `admin_stock_batches`？如果写一条“预览批次”，会带来哪些清理/幂等/审计问题？
2. 预览返回每行错误而不是遇到第一条就抛异常，对管理台有什么价值？服务端执行是否也应该如此？
3. 预览通过后库存被订单扣减，正式执行失败——这是 bug 还是预期？调用方应如何处理？
4. `availableAfter` 为什么只是预计值？它能否作为后续执行的乐观锁版本？
5. 预览与执行分别需要什么权限/CSRF/幂等？为什么预览不需要 Idempotency-Key？

## 4. 独立开发任务

**任务：CSV 批量导入 dry-run。**

要求：

- 上传 UTF-8 CSV（头 `productId,delta,reason`）；
- 限制 1MB/100 行；
- 逐行返回行号/错误；
- dry-run 不写库；
- 正式执行仍全有或全无；
- 同 Idempotency-Key 重放；
- 补文件大小/编码/重复/权限测试。

## 5. 故障定位练习

**场景**

预览显示全部可用，正式提交却返回 `STOCK_INSUFFICIENT`。请排查：

1. 先查哪三个证据？
2. 如何区分“预览后库存变化”“预览与执行用了不同门店”“执行条件漏了 store_id”“预览没有重新查库存”？
3. 给出两条 SQL/HTTP 证据。
4. 这是否需要修复？修复应放在前端、执行 SQL 还是预览锁？

## 6. 脱稿口述题

用 90 秒解释：

> “为什么 dry-run 必须只读？逐行预览与全有或全无执行如何配合？预览通过后库存变化怎么办？”

要求：

- 提到 TOCTOU、条件更新、幂等；
- 说明一个错误码；
- 不照读代码。
