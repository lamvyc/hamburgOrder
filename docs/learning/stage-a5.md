## 1. 知识定位

层级：**L2 — 取消状态机、库存释放、批处理、竞态、幂等扫描、索引**。

本轮真实用到了：

- WAIT_PAY → CANCELLED
- 条件 UPDATE 作为唯一状态闸门
- reserved → available 释放
- RELEASE 库存流水
- CONCURRENT payment/cancel
- 定时任务与 REQUIRES_NEW
- 重复扫描不重复释放
- `(status, expires_at, id)` 索引与 EXPLAIN
- 顾客/员工权限

## 2. 一句话本质

A5 的本质不是“加一个取消按钮”，而是：**取消和支付争夺同一个订单状态闸门，只有赢家能写终态、动库存、写事件；超时扫描也必须遵守同一套数据库条件。**

## 3. 阅读问题

1. 顾客取消和支付并发生效时，为什么最终只能有一种订单状态和一种库存终态？条件 UPDATE 的条件应该包含什么？
2. 取消时库存为什么是 `available + qty, reserved - qty`？如果只释放 reserved、不增加 available，会怎样？如果重复释放，会怎样？
3. 超时扫描为什么每个订单使用 REQUIRES_NEW？如果一个订单库存释放失败，应该影响同一批其他订单吗？
4. 两个扫描器同时拿到同一个过期订单 ID，为什么不会重复释放？`affected rows=0` 代表哪些合法情况？
5. 顾客取消自己的订单、其他顾客取消、员工取消、重复取消分别应返回什么？为什么其他顾客用 404 而不是 403？

## 4. 独立开发任务

**任务：新增 ADMIN 只读“过期未支付订单审计”接口。**

目标：

```text
GET /api/admin/orders/stale?limit=50&beforeExpiresAt=
```

要求：

- 仅 ADMIN；
- 只读，不修改订单或库存；
- 返回订单号、门店、过期时间、reserved 件数、订单金额；
- 稳定游标分页，不能用 OFFSET；
- 和 A5 扫描器共享“过期”定义；
- 补角色、分页、与扫描器结果一致性的测试；
- 记录 EXPLAIN，说明使用的索引。

不要提供管理员强制取消或手动释放库存。

## 5. 故障定位练习

**场景**

支付和取消几乎同时请求，数据库最终订单是 CANCELLED，但库存流水里同时出现 COMMIT 和 RELEASE；reserved 出现负数或 available 比预期多。

请排查：

1. 先查哪三个证据？
2. 如何判断是“状态更新没有条件”“库存操作没在同一事务”“失败方仍然执行了库存逻辑”“重复扫描”，还是“RESERVE 本身之前就错误”？
3. 给出两条 SQL 证据与预期终态。
4. 修复应放在 Service、SQL 条件、事务边界还是数据库约束？说明边界。

## 6. 脱稿口述题

> “取消和支付如何竞争？取消如何释放库存？超时扫描如何避免重复释放？为什么这些保证必须在数据库而不是按钮或内存锁里？”

要求：

- 提到条件 UPDATE、影响行数、REQUIRES_NEW、RELEASE、索引；
- 说明 409/404/403；
- 明确区分“任务执行了”和“业务结果只发生一次”。
