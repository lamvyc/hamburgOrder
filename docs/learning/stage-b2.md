## 1. 知识定位

层级：**L2/L3 — 管理端权限、乐观锁、条件更新、库存审计、前后值记录**。

本轮用到了：

- product.version / stock.version
- 条件 UPDATE + affected rows
- 409 VERSION_CONFLICT
- 库存不能为负
- ADJUST 流水与 order_id NULL
- 操作者与原因审计
- ADMIN 角色边界
- 管理台与对话框按需组件注册

## 2. 一句话本质

B2 的本质不是“管理员能改数字”，而是：**每次管理写入必须证明自己基于最新版本、只能成功一次、留下可追溯的前后值和操作者。**

## 3. 阅读问题

1. 为什么商品和库存使用两个独立版本，而不是一个版本？哪个操作会同时影响两者？
2. 乐观锁的条件 UPDATE 如何避免“后保存的人覆盖先保存的人”？如果只在 Service 里比较版本再更新，会有什么窗口？
3. 库存调整为什么只改 available、不改 reserved？如果管理员把 available 调到 0，但 reserved 还有 2，系统状态是什么含义？
4. 为什么库存调整写 `stock_logs`，还要写 `admin_audit_logs`？两者各自回答什么问题？
5. 为什么 `/api/admin/**` 不能只靠前端路由守卫？顾客/员工/未登录分别应返回什么？

## 4. 独立开发任务

**任务：新增“门店接单开关”，使用门店版本与审计。**

要求：

- 新增 `stores.version`；
- `PATCH /api/admin/stores/{storeId}`，请求包含 `acceptingOrders` 与 `version`；
- 条件更新 + affected rows；
- 旧版本 409；
- 写门店审计；
- 关闭接单后，顾客下单返回 `STORE_NOT_ORDERABLE`；
- 员工工作台仍能看到门店，但不能修改；
- 补并发、权限、审计测试。

不要实现门店新建/删除。

## 5. 故障定位练习

**场景**

管理员 A 把价格从 32 改为 33，管理员 B 同时把价格从 32 改为 34。最终数据库价格是 34，但审计只有 B 的记录，版本只 +1。

请排查：

1. 先查哪三个证据？
2. 如何区分“没有版本条件”“版本比较在事务外”“审计与更新不在同一事务”“B 的审计覆盖了 A”？
3. 给出两条 SQL 证据。
4. 修复应放在 SQL、Service、事务还是前端刷新？
